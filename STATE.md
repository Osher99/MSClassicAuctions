## Cloud Functions (region: us-central1)

| Function | Type | Trigger | Purpose |
|---|---|---|---|
| `contactForm` | v2 HTTPS (`onRequest`) | POST to `/contactForm` (hosting rewrite) | Sends the About-page contact form as an email |
| `notifyOnUserCreate` | v2 Firestore (`onDocumentCreated`) | new doc at `users/{userId}` | Sends welcome email (to the new user) + admin notification, right after signup |
| `getMarketplaceStats` | v2 HTTPS (`onRequest`) | GET `/getMarketplaceStats` (hosting rewrite) | Public counts (users / active listings / total listings) for the homepage stats section, read server-side via Admin SDK |

Both:
- Read `EMAIL_USER` / `EMAIL_PASS` secrets, send via `nodemailer` over Gmail SMTP.
- `maxInstances: 5` — cost/abuse ceiling, not a real capacity limit.
- Source: `functions/src/index.ts` only (`functions/index.ts` at the repo
  root was old v1 dead code — deleted). `functions/lib/` is build output,
  gitignored, regenerated by the `predeploy` hook in `firebase.json` on
  every `firebase deploy --only functions` — you never need to build it
  by hand.

`contactForm` also has a Firestore-backed per-IP rate limit: max 3
requests / 15 minutes, tracked in the `rateLimits` collection (fails
open if the Firestore check errors, so a hiccup there never blocks a
real user).

**Why `notifyOnUserCreate` is a Firestore trigger, not an auth trigger:**
the natural choice (`beforeUserCreated` from `firebase-functions/v2/identity`)
is a *blocking* function, and blocking functions require the Firebase
project to be upgraded to Google Cloud Identity Platform (GCIP). This
project is on plain Firebase Auth, and deploying a blocking function
against it fails with `Blocking Functions may only be configured for
GCIP projects` — confirmed by hitting that error directly. Firing off
the `users/{userId}` Firestore write instead (already happens right
after signup via `createUserProfile`) gets the same "email on signup"
behavior with zero GCIP dependency.

## Secrets (Secret Manager, via `firebase functions:secrets:*`)

- `EMAIL_USER` = `msclassicfm@gmail.com`
- `EMAIL_PASS` = a Gmail **App Password** for that exact account (16 chars,
  no spaces). Requires 2-Step Verification enabled on `msclassicfm@gmail.com`
  specifically — an app password generated while logged into a *different*
  Google account will authenticate-reject with `535 Invalid login`, it
  won't error at creation time.
- After rotating either secret, you must `firebase deploy --only functions`
  — a running function keeps using the secret *version* it was deployed
  with, it does not pick up a new value on its own.

## Environment files

| File | Loaded when | Contents | Committed? |
|---|---|---|---|
| `.env` | always (build + dev) | Real Firebase web-app config | No (gitignored) |
| `.env.development.local` | `vite dev` only (mode `development`) | Emulator-friendly placeholder values, `VITE_FUNCTIONS_BASE_URL=http://localhost:5001` | No (gitignored) |
| `.env.example` | never (template) | Placeholder key names for onboarding | Yes |

This used to be `.env.local` instead of `.env.development.local`, which
was a real bug: Vite loads `.env.local` in **every** mode, including
production builds. A plain `npm run build` was silently bundling the
placeholder Firebase API key into the deployed site, breaking login in
production. Renamed to scope it to dev-only. If you ever see
`API key not valid` on the live site, check whether something
reintroduced a `.env.local` and rebuild.

Note: `.env.development.local`'s current values are emulator-oriented
placeholders. Running `npm run dev` alone (without also running
`firebase emulators:start`) means Auth/Firestore/Functions calls from
localhost will fail — this is expected, not a regression.

## Item data source

`src/services/itemsData.service.ts` fetches the full item+scroll catalog
from `https://osmsdataexplorer.com/data/current/items.json` (~1900
entries) once per browser session (module-level cache), then filters
client-side — no more per-keystroke network calls to the old
`maplestory.io` API (deleted, `src/services/maplestory.service.ts` no
longer exists). Images: `.../images/items/{id, zero-padded to 8 digits}.png`.

Category mapping (source → app's internal vocabulary, kept identical to
what's already stored on existing `Listing` documents so no data
migration was needed): `Equipment→Equip`, `Consumable→Use`, `Etc→Etc`,
`Setup→Etc`. The source's separate `scrolls` array is merged in as
synthetic `Use`/`Consumable`/`Scroll` items so existing scroll-success-rate
auto-fill logic keeps working unchanged.

## Chat typing indicator

`conversations/{id}.typing` is a map of `uid → epoch ms of last keystroke
(or null once cleared)`, written (throttled to ~1 write / 2s) from
`ChatPage`'s input `onChange`, and cleared explicitly on send. Shown both
in the open chat (`ChatPage`) and in the conversation list (`ChatListPage`,
as a "typing..." replacing the last-message preview) via the shared
`useOtherTypingExpiry` hook in `useChat.ts`.

**Important:** that hook deliberately never compares one device's
timestamp to another device's `Date.now()` — two browsers' clocks can
drift by more than the expiry window, which silently hides the
indicator with no error anywhere. Instead, each viewer starts its own
local expiry countdown the moment a *change* in the timestamp arrives,
measured entirely on its own clock. If you touch this again, keep that
invariant — cross-device wall-clock comparisons are the failure mode
that bit us here.

## Marketplace stats section

Homepage (`ListingsPage`) shows an animated count-up (`useCountUp`,
`requestAnimationFrame`-based, no library) of Users / Active Listings /
Total Listings, backed by `getMarketplaceStats`. The counter only starts
once the section scrolls into view (`IntersectionObserver`) — if you
refactor `MarketplaceStatsSection`, keep the observed `<div ref=...>`
rendering unconditionally (not gated behind the stats-loaded check);
gating it caused the ref to be `null` when the observer effect first
ran, so it silently never attached and the numbers stayed at 0 forever.
